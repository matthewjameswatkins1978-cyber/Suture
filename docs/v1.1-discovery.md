# Threadmoth 1.1 discovery surface

> **Historical design record.** This page records the discovery model introduced with protocol 1.1. Threadmoth 1.9 still follows the same self-describing philosophy, but current fields, coverage levels and protocol versions are documented in [Coverage](coverage.md), [Protocol](protocol.md), and the runtime itself.

The 1.1 binary was designed to be self-describing. A caller with no repository documentation could use this sequence:

```text
threadmoth help
threadmoth capabilities --json --all
threadmoth examples
threadmoth schema request --json
threadmoth suggest path/to/file --goal set-value --at SELECTOR
```

That design remains: `help` explains the command map, `capabilities` reports the runtime provider/capability graph, `examples` emits request examples that deserialize through the same Rust request types used by execution, and `schema` exposes generated machine contracts with deterministic identity.

Threadmoth 1.9 additionally exposes path-scoped coverage metadata such as target kind, detection basis, understanding level, preservation level and explicit fallback routes.

Every refusal and relevant failure certificate includes a stable `reason_code`. Use `threadmoth explain REASON_CODE --json` for machine-readable recovery guidance. For a refusal certificate saved as `refusal.json`, use:

```text
threadmoth suggest --from-refusal refusal.json
```

Suggestions are deterministic skeletons only. They never invoke an LLM, network, subprocess or mutation, and they never loosen a caller's budget.
